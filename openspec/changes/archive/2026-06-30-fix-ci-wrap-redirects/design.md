## Context

`make init` runs `meson subprojects download` (Makefile line 81) to fetch the
top-level wraps before `meson setup`. On a clean clone (CI) this aborts:

```
ERROR: wrap-redirect subprojects/frida-core/subprojects/libgee.wrap filename does not exist
```

## Root cause

`subprojects/libgee.wrap` is a committed `[wrap-redirect]`:

```
[wrap-redirect]
filename = frida-core/subprojects/libgee.wrap
```

Meson loads every `subprojects/*.wrap` and resolves each `wrap-redirect`'s
`filename` eagerly — before downloading anything. On a clean clone
`subprojects/frida-core/` does not exist yet, so the target
`frida-core/subprojects/libgee.wrap` is absent and meson errors out.

Seven such redirects are committed: `libgee`, `libnice`, `libpsl`, `libsoup`,
`quickjs`, `tinycc`, `usrsctp`. Their targets live inside `frida-core/`,
`frida-gum/`, or `libsoup/` — sibling subprojects fetched later.

## Why the redirects exist at all

They are **transitive** wraps. When a parent wrap (e.g. `frida-core.wrap`)
declares a `[provide]` section, `meson subprojects download` writes a
`[wrap-redirect]` for each provided subproject into the root `subprojects/`
directory so that the root project can depend on the transitive name. They are
build artifacts, not source — `meson` regenerates them during `meson setup`.

The `subprojects/.gitignore` documents this:

```
# Transitive .wrap files are auto-generated by `meson subprojects download`
# from the parent wraps' [wrap-redirect]/[provide] sections. Ignore them all
# and re-allow only the wraps we author and commit.
```

but then contradicts itself by re-allowing the seven redirects. They were
committed in `9a8e999` (`feat(inject)`) and never removed. The archived change
`2026-06-28-fix-provisioning-wraps` updated the `provisioning` spec to forbid
redirect wraps and listed their removal as a task, but the code fix was never
applied — the files stayed in the tree.

## Why it is masked locally

On a developer machine `subprojects/frida-core/` is already fetched, so the
redirect target exists and `meson subprojects download` succeeds. CI clones
clean, so the target is absent.

## Fix

Remove the seven committed `[wrap-redirect]` wraps and stop re-allowing them in
`subprojects/.gitignore`. They are regenerated by meson during `meson setup`.
Keep re-allowing only the wraps the project authors:

- `frida.wrap`, `frida-core.wrap`, `frida-gum.wrap` — direct `wrap-git`
  dependencies pinned by the project.
- `monocypher.wrap` — direct `wrap-git` dependency with a committed
  `patch_directory`.
- `selinux.wrap` — a top-level override of frida-core's selinux wrap, carrying a
  `patch_directory = selinux` that fixes libselinux's missing libsepol
  dependency (the spec's "Top-level wrap overrides a transitive subproject's
  wrap" scenario).

## Alternatives considered

- **Keep the redirects, download frida-core first.** Would require splitting
  `meson subprojects download` into a frida-core-only fetch then a full download,
  fighting meson's wrap model. The redirects are redundant (transitive deps
  resolve from each subproject's own bundled wraps during `meson setup`), so
  removing them is simpler and matches the spec.
- **Make the redirects point at a committed copy.** Duplicates upstream wraps
  and breaks on every frida bump. Rejected.

## Verification

- `git ls-files subprojects/*.wrap` lists only `frida.wrap`, `frida-core.wrap`,
  `frida-gum.wrap`, `monocypher.wrap`, `selinux.wrap`.
- `meson subprojects download` exits 0 on a tree with `subprojects/frida-core/`
  removed (simulating a clean clone).
- `make init` reaches `meson setup` without the `wrap-redirect … does not exist`
  error.

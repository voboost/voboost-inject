## Why

The `attach-launcher` integration scenario asserts the daemon injects an agent
into the already-running `com.qinggan.app.launcher` stub and reports
`state: active`. But the signed fixture manifest (`test/fixtures/manifest.json`,
generated by `gen-fixtures.sh`) declared no agent for that process — only
`wm-viewport` (system_server), `settings-menu` and `low-speed-sound`
(vehiclesetting). With nothing to inject into the launcher, the daemon left it
alone and the scenario could never pass. The fixture manifest is the daemon's
whitelist of agent ids a plan may request, so a scenario targeting the launcher
needs a launcher agent in the fixture manifest.

## What Changes

- **`test/fixtures/gen-fixtures.sh`** emits one more agent, `launcher-echo`
  (`agents/launcher-echo.js`, process `com.qinggan.app.launcher`, payload a
  minimal `send({ ok: true, agent: 'launcher-echo' })` stub), so the signed
  fixture manifest and agent payload cover the `attach-launcher` scenario.
- The manifest is re-signed by `gen-fixtures.sh` (unchanged mechanism); the
  regenerated `manifest.json` + `manifest.sig` + `agents/launcher-echo.js` are
  committed.

## Impact

- **`attach-launcher`:** the daemon now has a launcher agent to inject, so (with
  the `find-pid-package-match` fix resolving the pid) the scenario reaches
  `state: active`.
- **Host tests:** unchanged — they look up specific ids (`wm-viewport`) and do
  not assert on the agent count, so adding `launcher-echo` breaks nothing
  (verified: 9/9 pass).
- **Other fixtures:** the APK/release-manifest fixtures are regenerated by the
  same script and pick up the new manifest hash automatically.

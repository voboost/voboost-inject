# voboost-inject

[English](README.md) | **Русский**

**voboost-inject** — корневой (root) компонент инъекций Voboost: единственный нативный
Vala-бинарь со встроенным [frida-core](https://frida.re) (движок QuickJS, без V8),
работающий от имени **root** и внедряющий криптографически **подписанные** агенты в
целевые процессы Android — обычно `system_server` и другие процессы фреймворка, до
которых не может добраться непривилегированное
[приложение Voboost](https://github.com/voboost/voboost).

Он запускается один раз при загрузке хуком `/system` init и работает как единый
резидентный демон всю сессию. Приложение Voboost сообщает ему, *какие* подписанные агенты
внедрять; voboost-inject проверяет каждый байт перед внедрением и никогда не доверяет
приложению в чём-либо критичном для безопасности.

> Поведенческие детали — в `openspec/specs/`. Этот README — пользовательский обзор;
> спецификации являются источником истины.

## Проект Voboost

voboost-inject — один компонент мультирепозиторной системы:

- [`voboost`](https://github.com/voboost/voboost) — непривилегированное Android-приложение
  (`ru.voboost`); поставляет агенты в своём APK и пишет `inject.json`.
- **`voboost-inject`** *(этот репо)* — root-демон; проверяет и внедряет подписанные агенты.
- [`voboost-script`](https://github.com/voboost/voboost-script) — JavaScript-агенты Frida и
  **подписанный манифест набора агентов**, в котором они поставляются.
- [`voboost-install`](https://github.com/voboost/voboost-install) — подготовку устройства:
  первичная установка бинаря демона, агентов и хука `/system` init.

Этот README описывает контракт демона и сборку. Авторство агентов и подписывание — в
[`voboost-script`](https://github.com/voboost/voboost-script); полная подготовка устройства —
в [`voboost-install`](https://github.com/voboost/voboost-install).

```sh
make init     # подготовка тулчейна, dev-ключа и frida-подпроектов
make build    # сборка для хоста (release, LTO, frida-core статически)

```

## Что он делает

- **Root-демон.** Единственный резидентный root-процесс, запускаемый при загрузке хуком
  `/system` init. Одиночный экземпляр гарантируется pidfile под `flock` (не сопоставлением
  имён процессов); второй экземпляр логирует конфликт и завершается без инъекций.
- **Встроенный frida-core.** Управляет frida-core внутри процесса через локальное
  устройство — без сокета, без вспомогательного процесса на каждую инъекцию. frida-core
  статически линкуется в бинарь с LTO; отдельной frida-библиотеки на диске нет.
- **Только подписанные агенты.** Каждый агент проверяется дважды перед запуском: манифест
  набора агентов сверяется с публичным ключом, вшитым в бинарь (ed25519), а каждый файл
  агента проверяется по sha256 против верифицированного манифеста. Проверка всегда включена
  — режима пропуска проверки нет.
- **Раннее внедрение.** Ещё не запущенные цели spawn-gate'ятся так, что агент загружается
  до того, как цель выполнит свой код; уже работающие цели подключаются (attach). Нецелевые
  процессы, пойманные глобальным spawn-gating, немедленно возобновляются без затрат на
  подключение.
- **Безопасность устройства.** Spawn-gated процесс всегда возобновляется, даже если инъекция
  не удалась (fail-open). Агенты изолированы друг от друга; падающий агент попадает под
  rate-limit и карантин, а порог массовой гибели вызывает глобальный panic-quarantine,
  останавливающий все инъекции. Рантайм kill-switch (`/data/voboost/run/disable`)
  останавливает всё и переводит демон в простой. (Механика и точные пороги: *Архитектура →
  Безопасность устройства*.)
- **OTA без перезагрузки устройства.** Агенты и сам бинарь демона обновляются на устройстве:
  агенты через атомарный обмен манифеста, ядро бинаря через content-addressed установку плюс
  чистое само-завершение, которое Android init превращает в перезапуск нового бинаря — без
  перезагрузки, с автоматическим откатом, если новый бинарь поднимается в деградированном
  состоянии. (Подробности: *Плоскости OTA-обновлений*.)

## Как это работает с приложением Voboost

Приложение Voboost ([`voboost`](https://github.com/voboost/voboost), пакет `ru.voboost`) —
обычное непривилегированное приложение в user-space. Оно распространяет себя само (не через
Play) и поставляет Frida-агенты внутри собственного APK.
Демон и приложение никогда не имеют общего сокета — они общаются **только через файлы**, в
двух строго разделённых зонах доверия на устройстве:

| Зона | Путь | Владелец | Кто пишет |
|------|------|----------|-----------|
| Root-зона (доверенная) | `/data/voboost` | root:root, `700` | только демон |
| Зона приложения (недоверенная) | `/data/user/0/ru.voboost` | приложение | приложение; демон пишет только статус |

Приложение **не может** читать, переименовывать или заменять что-либо в `/data/voboost`.
Демон (работающий как root) может читать зону приложения, но рассматривает каждый
прочитанный байт как недоверенный и перепроверяет перед действием.

### Файлы передачи

Все три файла специфицированы в `openspec/specs/app-interface`.

- **`inject.json`** *(приложение → демон, зона приложения)* — единственный файл инструкций
  приложения. Он содержит гейт `startup`, kill-switch `disabled` и список флагов `enabled`
  для каждого агента плюс непрозрачный blob `config`, который демон дословно передаёт
  каждому агенту:

  ```json
  {
    "startup": "auto",
    "disabled": false,
    "agents": [
      { "id": "wm-viewport", "enabled": true, "config": { "scale": 1.2 } }
    ]
  }
  ```

  `"startup": "none"` заставляет демон завершиться без инъекций; любое другое значение (или
  отсутствие поля) позволяет ему работать. Демон определяет целевой `process` каждого агента
  из **верифицированного манифеста**, никогда из этого плана; `config` — непрозрачные байты,
  ограниченные только размером (64 КиБ на агента, 1 МиБ на весь файл).

- **`inject-status.json`** *(демон → приложение, зона приложения)* — исходящий статус
  демона, записываемый атомарно (temp + rename, без следования по symlink):

  ```json
  {
    "daemon": "1.0.0-beta1",
    "manifest": 1,
    "state": "ready",
    "killed": false,
    "panic": false,
    "injections": [
      { "id": "wm-viewport", "process": "system_server", "state": "active" }
    ]
  }
  ```

  `daemon` — версия демона; `manifest` — `version` активного манифеста (см. *Написание
  агентов*); `state` — `ready` или `degraded`; `injections[].state` — одно из `active`,
  `failed`, `skipped-coexist`, `waiting`, `quarantined`.

- **`staging/` + `core-update-ready`** *(приложение → демон, зона приложения)* — область
  OTA-стейджинга. Приложение скачивает обновлённые агенты/манифест, записывает их в
  `staging/` и создаёт маркер `core-update-ready` последним. Демон перепроверяет всё против
  своего вшитого ключа перед заменой в доверенную зону.

### Модель доверия

Единственный якорь доверия демона — публичный ключ, **вшитый в бинарь**. Он никогда не
читает ключ с диска. Манифест набора агентов подписан соответствующим приватным ключом и
проверяется вшитым публичным ключом; каждый файл агента затем проверяется по sha256 против
этого верифицированного манифеста. Тот же набор ключей подписывает OTA release-манифест.
Приложение не подписывает ничего, чему демон доверяет на вере, — оно только доставляет
материал, который демон перепроверяет против вшитого ключа.

## Архитектура

### Конечный автомат демона

```
INIT -> VERIFY_SELF -> READY
                    \-> DEGRADED (только наблюдение, ничего не внедряет)
```

При загрузке демон:

1. Получает эксклюзивный `flock` на pidfile (одиночный экземпляр).
2. Читает поле `startup` из `inject.json` — `"none"` завершает немедленно.
3. Входит в VERIFY_SELF: проверяет ed25519-подпись манифеста против вшитого ключа, затем
   проверяет каждый sha256 агента.
4. При успехе входит в READY, включает spawn-gating и начинает внедрение.
5. При неудаче (неверная подпись, несовпадение хэша или ошибка открытия frida-core) входит в
   DEGRADED — только наблюдение, без инъекций.

### Жизненный цикл каждой цели

```
GATE (spawn-gated) или ATTACH (уже работает)
  -> INJECT (JavaScript через per-process QuickJS session script)
  -> MONITOR (наблюдение за гибелью, реинъекция в рамках safety-бюджета)
```

- Каждый агент выполняет JavaScript на QuickJS-рантайме frida-core через `create_script`,
  на per-process session script.
- Агент с `boot: true` в манифесте откладывается до `sys.boot_completed=1`; остальные
  внедряются немедленно.

### Безопасность устройства

- **Гарантированное возобновление.** Spawn-gated процесс всегда возобновляется, даже при
  неудаче инъекции или таймауте.
- **Изоляция по агентам.** Падение одного агента не влияет на другие и не роняет цель.
- **Rate-limit + карантин.** Повторяющиеся гибели цели для одной пары (агент, процесс)
  вызывают экспоненциальный backoff, затем карантин (агент прекращает внедрение; цель
  работает немодифицированно).
- **Panic-quarantine.** Массовая гибель целей на устройстве вызывает глобальную остановку —
  все инъекции прекращаются.
- **Пропуск сосуществования.** Если `/proc/PID/maps` показывает уже присутствующего
  стороннего Frida-агента, инъекция пропускается для этого процесса.
- **Рантайм kill-switch.** Файл `/data/voboost/run/disable` или флаг плана `disabled`
  останавливает все инъекции и переводит демон в простой. Деактивация kill-switch требует
  перезапуска демона; инъекции не возобновляются автоматически.

### Пороги безопасности

Правила безопасности устройства выше срабатывают при фиксированных порогах, вшитых в демон
(полная семантика в `openspec/specs/device-safety`):

- **Rate-limit реинъекций.** Не более **3** попыток внедрения за **5-минутное** окно на пару
  (агент, процесс); 4-я в окне переводит этого агента в карантин (fail-open — цель
  продолжает работать немодифицированно).
- **Экспоненциальный backoff.** Каждая неудачная попытка задерживает следующую на удваиваемый
  интервал с потолком **30 минут**; успешная инъекция сбрасывает его.
- **Panic-quarantine.** **8** гибелей целей за **5-минутное** скользящее окно вызывает
  глобальную остановку всех инъекций до перезапуска демона.

### Плоскости OTA-обновлений

| Плоскость | Механизм | Перезапуск? |
|-----------|----------|-------------|
| Агенты | Атомарный обмен манифеста + реинъекция | Нет |
| Ядро | Content-addressed установка + само-завершение; init перезапускает новый бинарь | Да |

- Обновления агентов применяются немедленно (перед первой инъекцией при загрузке или в
  рантайме при появлении маркера `core-update-ready`).
- Обновления ядра переименовывают работающий бинарь в `voboost-inject.prev`, устанавливают
  новый бинарь по стабильному пути запуска `voboost-inject` и само-завершаются; Android init
  перезапускает сервис. Предыдущий бинарь сохраняется как `.prev` для отката.
- Если новый бинарь запускается в DEGRADED, он автоматически откатывается к предыдущему.
- Маркер `core-update-ready` одноразовый: поглощается после любой попытки применения (успех
  или верифицированная неудача).

## Безопасность

- **Якорь доверия вшит.** Единственный ключ проверки встроен в бинарь при сборке; демон
  никогда не загружает ключ с диска, а проверка подписи + sha256 всегда включена — режима
  пропуска проверки нет.
- **Эшелонированная защита root-зоны.** `/data/voboost` и вся цепочка родительских каталогов
  принадлежат root, поэтому непривилегированное приложение не может читать, переименовывать
  или заменять доверенное состояние. VERIFY_SELF дополнительно перепроверяет, что root-зона
  принадлежит root и не группо-/мирово-доступна для записи, входя в DEGRADED (ничего не
  внедряет) при неудаче. SELinux на этом устройстве permissive, так что эти Unix-права —
  несущий слой, а не вторичная проверка.
- **Недоверенная зона приложения.** Всё, что демон читает из зоны приложения (`inject.json`,
  `staging/`), перепроверяется перед использованием. Единственный файл, который демон пишет
  туда — `inject-status.json` — записывается атомарно во временный файл, открытый с
  `O_NOFOLLOW`, и переименовывается на место, чтобы symlink, предсозданный приложением, не
  мог перенаправить запись на root-принадлежащий файл.
- **ed25519 через Monocypher.** Проверка подписей — подпроект Monocypher (без системной
  криптографии на устройстве); frida-core статически линкуется, так что нет отдельной
  frida-библиотеки для подмены.
- **Минимальная поверхность атаки.** Демон не открывает слушающий сокет и не запускает
  вспомогательный процесс на каждую инъекцию — вся работа frida-core идёт внутри процесса
  над локальным устройством.

## Написание агентов

Агенты создаются, собираются и подписываются в
[`voboost-script`](https://github.com/voboost/voboost-script); этот раздел описывает
per-agent контракт, который проверяет демон, чтобы манифест был узнаваем со стороны демона.
Инструменты для сборки манифеста и подписи соответствующим приватным ключом — часть
[`voboost-script`](https://github.com/voboost/voboost-script).

Агент — это JavaScript, выполняемый на QuickJS-рантайме frida-core (см. *Жизненный цикл
каждой цели* выше). Он проверяется по подписи манифеста + sha256 и получает тот же
непрозрачный `config`. Каждый поставляемый агент — JavaScript (см.
[`voboost-script`](https://github.com/voboost/voboost-script)).

Манифест набора агентов (`manifest.json`, подписанный в `manifest.sig` и поставляемый внутри
APK приложения) — это объект с `version`, опциональным `daemon` и массивом `agents`:

```json
{
  "version": 1,
  "daemon": "1.0.0-beta1",
  "agents": [
    {
      "id": "wm-viewport",
      "channel": "agents",
      "file": "agents/wm-viewport.js",
      "sha256": "86e413ce702abb872718569c06a2e01c52553ad35953c6df122e007d3146a87a",
      "process": "system_server",
      "boot": false
    }
  ]
}
```

`version` — версия манифеста, возвращаемая как `"manifest"` в `inject-status.json`; `boot:
true` откладывает агента до завершения загрузки устройства. Манифест подписан приватным
ключом, соответствующим вшитому публичному ключу демона; демон проверяет подпись, затем
sha256 каждого агента против неё (см. `openspec/specs/trust-verification`).

### Агент (QuickJS)

```js
// agents/wm-viewport.js — выполняется на встроенном движке QuickJS.
// Демон вызывает rpc.exports.init(stage, parameters) при загрузке,
// с parameters.config = "config" этого агента из inject.json.
rpc.exports = {
  init(stage, parameters) {
    const { scale } = parameters.config;   // e.g. { "scale": 1.2 }
    Java.perform(() => {
      // ...установка хуков на класс фреймворка...
    });
  }
};
```

### Обмен сообщениями агент ↔ демон

Демон общается с агентом по протоколу `frida:rpc` поверх `Script.post`/`message`:

- **демон → агент:** при загрузке демон вызывает `rpc.exports.init(stage, parameters)` с
  `parameters.config` равным `config` агента из `inject.json` (он сам отправляет сообщение
  `["frida:rpc", …, "call", "init", …]` — нужно только определить экспорт `init`).
- **агент → демон:** `send(payload)` из агента попадает в обработчик `script.message`
  демона и записывается в root-only лог под `agent/<id>`. Это однонаправленный канал
  наблюдения — демон не вызывает обратно после `init`.

```js
rpc.exports = {
  init(stage, parameters) {
    const { scale } = parameters.config;
    send({ event: 'ready', scale });        // агент -> демон (логируется)
    Java.perform(() => {
      // ...установка хуков на класс фреймворка...
    });
  }
};
```

## Сборка

### Предварительные требования

Все необходимые инструменты устанавливаются или собираются через `make init`:

- Компилятор Vala (`valac`) — frida-патченная сборка (суффикс версии `-frida`)
- meson (>= 1.1.0), ninja, git
- openssl (ed25519 ключи/подпись), bsdiff, uncrustify
- `io.elementary.vala-lint` — собирается из зафиксированной ревизии исходников (тег
  `0.1.0`); **нет пакета Homebrew/apt** для него
- Android NDK — внешний; установите `ANDROID_NDK_HOME` для сборки под устройство

Проверка, что всё на месте:

```sh
make check
```

### С чистого клона

```sh
make init     # подготовка всего окружения (OS-пакеты, vala-lint, frida valac, dev-ключ, setup)
make build    # сборка бинаря демона (хост, release, LTO, frida-core статически)
make test     # тесты на стороне хоста (без устройства)
```

`make init` выполняет три шага по порядку:

1. **toolchain** — устанавливает OS-пакетные инструменты, собирает `io.elementary.vala-lint`
   из зафиксированного тега исходников, собирает frida-патченный `valac` (требуется для
   frida-core) и подтягивает зафиксированные frida-подпроекты. Инструменты устанавливаются в
   `.tools/` (проектно-локально, gitignored); Makefile добавляет это в `PATH`.
2. **key-dev** — генерирует локальный ed25519 dev-ключ в `config/key-dev-private.pem`
   (gitignored) и `config/key-dev-public.pem` (коммитится), используемый для вшивания
   публичного ключа в бинарь.
3. **setup** — запускает `meson setup build`.

### Заметки по ОС

**macOS (Homebrew)** — `make init` выполняет
`brew install vala meson ninja bsdiff uncrustify json-glib glib pkg-config`,
затем собирает vala-lint и frida-патченный valac из исходников.

**Linux (Ubuntu/Debian)** — `make init` выполняет `apt-get` (через `sudo`) для эквивалентных
пакетов (вкл. `libvala-dev`, `libgee-0.8-dev`, `libjson-glib-dev`), затем собирает vala-lint
и frida-патченный valac из исходников.

**Windows** — используйте WSL2 + Ubuntu (кросс-тулчейн Android Linux-native):

```pwsh
wsl --install -d Ubuntu
```

затем следуйте пути Linux внутри WSL2.

### Сборка для хоста vs. устройства

Сборки только release (без debug-конфигурации):

```sh
make build          # сборка для хоста: release, LTO, frida-core статически, динамические хост-библиотеки (для тестов)
make build-android  # сборка под устройство: arm64-v8a, frida/glib-стек статически, bionic динамически
```

`make build` сохраняет таблицу символов (нужна хост-тестам); strip применяется при установке
(`meson install --strip`). Сборка под устройство самодостаточна для frida/glib-стека: каждый
подключённый подпроект (frida-core, glib, gio, json-glib, monocypher, ...) линкуется
статически через глобальный `default_library=static`, поэтому glib/gio/json-glib на
устройстве не поставляется. Системные bionic-библиотеки (libc, liblog, libz, libm, libdl)
линкуются динамически — NDK r29 не содержит статического bionic, а bionic всегда присутствует
на Android. Демон local-backend-only, поэтому `frida-core:connectivity` (TLS/ICE) отключён.

`make build-android` требует Android NDK в `ANDROID_NDK_HOME`; PATH тулчейна NDK выводится
автоматически (без ручной настройки PATH). CI фиксирует NDK **r29** — releng frida-core
17.11.0 требует точно мажорную версию 29 (`NDK_REQUIRED=29`); r27/r27d отвергаются.
Используйте тот же локально для воспроизводимых сборок под устройство.

Оба `make setup` и `make build-android` конфигурируют через собственный meson-fork frida
(поставляется `make init` из `releng/meson` подмодуля `frida-core`), а не системный meson —
`quickcompile` frida-gum (`native: true`) требует сборки QuickJS-подпроекта для build-машины,
что делает только meson frida. frida-meson запускается через `PYTHON_FOR_MESON` (по
умолчанию `/usr/bin/python3`), который должен поставлять stdlib-модуль `distutils` (удалён в
Python 3.12) — `gdbus-codegen` glib импортирует его.

### Линт и тесты

```sh
make lint      # io.elementary.vala-lint + uncrustify --check (гейт)
make lint-fix  # uncrustify --replace (канонический стиль на месте)
make test      # meson test (на стороне хоста, молча при успехе)
```

`make lint` сначала проверяет, что оба линтера в `PATH`; если какого-то нет, он говорит
запустить `make init` вместо падения с `command not found`.

## Установка / развёртывание

### Расположение на устройстве

На подготовленном устройстве демон владеет root-зоной `/data/voboost`:

```
/data/voboost/
  voboost-inject                стабильный путь запуска, который exec'ит хук init
  voboost-inject.prev           предыдущий core-бинарь, хранится для OTA-отката
  manifest.json + manifest.sig  активный подписанный манифест набора агентов
  manifest.json.prev + .sig     откатная копия на одну глубину
  agents/<...>                  верифицированные payload'ы агентов
  run/disable                   рантайм kill-switch (наличие = остановить всё)
  run/core-switch-pending       маркер OTA core-swap
  logs/inject-YYYY-MM-DD.log    root-only ежедневный лог (хранится 7 дней)
```

Зона приложения `/data/user/0/ru.voboost/` содержит `inject.json`, `inject-status.json` и
OTA-область `staging/`.

### Первичная подготовка

Полная подготовка устройства — размещение верифицированного бинаря в
`/data/voboost/voboost-inject`, раскладка агентов и подписанного манифеста и установка хука
`/system` init — находится в
[`voboost-install`](https://github.com/voboost/voboost-install). Этот репо только определяет
контракт, которому подготовленное устройство должно соответствовать: хук init один раз
exec'ает стабильный путь запуска, сконфигурированный на **перезапуск при выходе** (не
`oneshot`). OTA core-обновление без перезагрузки и чистое восстановление после падения оба
зависят от перезапуска демона init'ом.

### Релизы, подпись и release-манифест

CI собирает release-бинарь, генерирует и подписывает OTA release-манифест и публикует оба.
Публичный ключ production-подписи — `config/release-public.pem` (коммитится мэйнтейнером);
соответствующий приватный ключ есть только в CI-секрете `SIGNING_KEY` и никогда не
коммитится.

Сгенерировать release-ключ:

```sh
openssl genpkey -algorithm ed25519 -out config/release-private.pem
openssl pkey -in config/release-private.pem -pubout -out config/release-public.pem
# сохраните config/release-private.pem как CI-секрет SIGNING_KEY, затем удалите локально
```

Release-манифест производится и подписывается Make-таргетами мэйнтейнеров (CI вызывает их
автоматически):

```sh
make release-manifest DIR=<release-dir> CHANNEL=<agents|core|app> VERSION=<semver>
make sign         KEY=<private.pem> FILE=build/release-manifest.json
make verify-sig   KEY=<public.pem>  FILE=build/release-manifest.json
```

Для `beta1` dev-ключ (`config/key-dev-*`) можно переиспользовать как release-ключ —
ротируйте перед настоящим релизом.

### После системного OTA

Системный OTA откатывает только `/system`, так что хук init теряется, пока `/data/voboost`,
демон и все агенты переживают. Оператор восстанавливает хук через `adb` (идемпотентно — хук,
уже содержащий блок, остаётся нетронутым):

```sh
make device-rearm HOOK=<путь хука init на устройстве>
```

Ничего не скачивается заново; инкрементальный OTA приложения/агентов независим от каденса
системного OTA.

## Логирование

Демон пишет в `/data/voboost/logs/inject-YYYY-MM-DD.log` (режим `600`, root-only) и хранит
логи **7 дней**. Каждая строка следует общему формату `yyyy-MM-dd HH:mm:ss.SSS [tag] src:
msg`, где тег — `[*]` (info), `[+]` (ok) или `[-]` (error). Пример:

```
2026-06-26 07:52:13.042 [*] main: SIGTERM: clean shutdown
2026-06-26 07:52:14.101 [+] frida: injected wm-viewport
```

Лог остаётся в root-зоне — приложение не может его читать, и демон никогда не пишет лог в
зону приложения.

## Диагностика

На root-устройстве (или `adb root` на userdebug-сборке) оператор может наблюдать и управлять
демоном напрямую:

```sh
# Статус демона (зона приложения — это же читает приложение):
adb shell cat /data/user/0/ru.voboost/inject-status.json

# Сегодняшний лог демона (root-зона):
adb shell cat /data/voboost/logs/inject-$(date +%F).log

# Остановить все инъекции сейчас (рантайм kill-switch); gated-процессы возобновляются:
adb shell touch /data/voboost/run/disable

# Возобновление: убрать kill-switch, затем перезапустить демон — инъекции НЕ
# возобновляются сами, требуется перезапуск:
adb shell rm /data/voboost/run/disable
#   затем перезапустить init-сервис (или перезагрузить), чтобы поднять демон
```

- `"state": "degraded"` в `inject-status.json` означает, что VERIFY_SELF или открытие
  frida-core не удалось — демон observe-only до перезапуска.
- `"panic": true` означает, что сработал глобальный panic-quarantine; он очищается только
  при перезапуске демона.
- Одиночный экземпляр гарантируется через `flock` на `/data/voboost/run/inject.pid`; второй
  запуск логирует конфликт и завершается.

## CI

### Push / PR (`ci.yml`)

Каждый push и pull request выполняется на `ubuntu-latest`:

1. `make init` — подготовка (кэшируется по зафиксированным ревизиям)
2. `make lint` — оба линтера
3. `make test` — хостовые unit-тесты
4. `make build` — release-only сборка для хоста для валидации

### Release (`release.yml`)

Запускается тегом `v*`:

1. `make init` — подготовка (кэшируется)
2. **Версионный гейт** — падает, если тег не совпадает с `v$version` из `meson.build`
3. `make lint` + `make test` — гейты качества перезапускаются (тег не может их обойти)
4. Настройка Android NDK (`r29`, SHA-зафиксированный action)
5. `make build-android` — arm64-v8a, полностью статически
6. `llvm-strip` бинаря устройства
7. `make release-manifest` — генерирует `build/release-manifest.json`
8. `make sign` + `make verify-sig` — подписывает CI-секретом `SIGNING_KEY`
9. Публикует `voboost-inject`, `release-manifest.json` и `.sig` как workflow-артефакты

## Версионирование

Версия живёт в `meson.build` `project(version: ...)` (единый источник истины, базовая
`1.0.0-beta1`). CI потребляет её и нигде не определяет. Поднимайте pre-release-постфикс
перед каждым release-тегом, затем пушьте соответствующий тег; release-workflow валидирует
`v$version == $tag` и падает при расхождении.

    1.0.0-beta1 -> 1.0.0-beta2 -> ... -> 1.0.0-rc1 -> 1.0.0

## Структура проекта

```
src/            исходники демона на Vala (модули + VAPI-биндинги)
test/           хостовые unit-тесты + фикстуры + план интеграционных тестов
config/         конфиги сборки (uncrustify, vala-lint, cross-file, dev/release ключи)
openspec/specs/ поведенческие спецификации (источник истины)
subprojects/    зафиксированные git-обёртки frida (подтягиваются make init)
.tools/         собранные инструменты (frida-патченный valac, vala-lint; gitignored)
```

Frida поставляется из зафиксированных git-обёрток в `subprojects/` (frida, frida-core,
frida-gum, все зафиксированы на теге `17.11.0`), подтягиваются и кэшируются на `make init`;
хардкоженного локального пути frida-исходников нет.

## Модули исходников

| Файл | Назначение |
|------|------------|
| `main.vala` | Точка входа: блокировка одиночного экземпляра, гейт запуска, GMainLoop, SIGTERM |
| `supervisor.vala` | Конечный автомат (INIT→VERIFY_SELF→READY/DEGRADED), оркестрация инъекций |
| `frida_controller.vala` | Управление frida-core в процессе: spawn-gating, attach, inject, resume |
| `manifest.vala` | Верифицированный парсер манифеста (ed25519 sig + JSON; id/process агента) |
| `plan_reader.vala` | Парсер недоверенного `inject.json`, валидируемого против манифеста |
| `trust_store.vala` | Проверка ed25519-подписи (Monocypher), проверка sha256 агентов |
| `safety.vala` | Rate-limit, карантин, panic-quarantine, пропуск сосуществования, kill-switch |
| `status.vala` | Атомарный писатель `inject-status.json` (temp + rename, без следования symlink) |
| `ota.vala` | OTA применение/откат: обмен манифеста агентов, core-установка + само-завершение |
| `app_zone_watcher.vala` | GFileMonitor на `inject.json` и `staging/core-update-ready` |
| `process_watcher.vala` | Событийное отслеживание целей через frida spawn/death-сигналы |
| `log.vala` | Root-only ежедневный лог, хранение 7 дней, общий формат |
